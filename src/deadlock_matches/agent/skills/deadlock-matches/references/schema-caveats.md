# Parquet table schema caveats

Per-table columns and verified traps for **hand-writing raw polars**. Check `deadlock schema --views` first. A metric view aggregates the table for you and already applies every caveat below, and each entry here names the view that covers its table. Read this file before querying a table directly when no view and no `queries` helper covers what you need. If you are relaying CLI output or reusing either one, you do not need it.

Tables live in `~/.local/share/deadlock-matches/parquet/`; `deadlock schema <table>` prints the columns for any of them.

## Tables

- `matches` / `players`:
  - `matches` has `average_badge_team0/1` — each team's average skill rating as a badge level (tier * 10 + level, 95 = Phantom 5; null when the protobuf omits it). `queries.skill_rating("average_badge_team0")` maps to labels. NO per-player skill rating exists anywhere in the metadata ("only you can see your Skill Rating" per the in-game help). Lobby averages in thin queues can sit well below a player's real badge — never present lobby average or deadlock-api mmr-history as the player's skill rating
  - `players` has `hero_id`, `won`, `lane` (starting lane color, yellow = west / blue = center / green = east, geometry-verified against movement; `assigned_lane` keeps the raw 1/4/6 ids) and `mvp_rank` (post-game awards: 1 = match MVP, always a winner; 2-3 = Key Player, 3 usually the best loser; 0 = no award). Your own games aggregate through the `my_games` view (`record_games` for the winrate window), and `queries.player_rows()` reads the table with the current `hero` display name. Post-game award stat cards live in their own `accolades` table (backs `deadlock match --accolades`)
  - `players.party`: 0 = queued solo, players sharing a nonzero id queued together, ids never cross teams. Valve removed the field from the metadata in mid-March 2026, so it is null on everything after — deadlock-api also has null for all recent matches. Older archived matches keep it as an unknown field that `extract.player_party` recovers; the API-json path (`from_api_json`) drops unknown fields, so API-backfilled matches are null regardless of age
  - <a id="players.abandon-reconnect"></a>`players.abandon_time_s`: game time in seconds when the player got the abandon strike, null = never flagged. It does NOT mean they stayed gone — a meaningful share of abandoners reconnect and keep playing. Damage growth between samples after the abandon is the ONLY valid reconnect signal: disconnected players keep earning passive souls and their queued build keeps auto-buying, and an abandoned hero gets farmed where it stands, so buys and deaths prove nothing. `queries.abandon_record` applies this — use it instead of hand-rolling
  - <a id="matches.game-mode"></a>`matches.match_mode` / `matches.game_mode` are two SEPARATE wire enums and both have to be filtered. **Deadlock has one matchmaking queue — there is no ranked/unranked split** — and it arrives as `match_mode == 1` (the protobuf name `Unranked` is a holdover). `match_mode == 2` is `PrivateLobby`, which for a pro means scrims and FACEIT; `4` is the retired ranked queue. The trap is `game_mode`: **`4` is Street Brawl, a different map and ruleset that still carries `match_mode == 1`**, so a `match_mode == 1` filter alone lets brawl games into ladder stats (the archive holds 12 of them, all on one alt in Feb 2026, 7-22 minute games — they read ~34 points below the real win rate for that account). Ladder performance needs `match_mode == 1 AND game_mode == 1`. Own-game views and `players.pool_games` / `pool_members` / `pool_builds` apply that pair at read time by default, including to old cumulative ledger rows; `queries.mode_context`, `my_games(match_mode=, game_mode=)`, CLI `--street-brawl` `(1, 4)`, or CLI `--private-lobby` `(2, 1)` selects another mode without merging. Tracked-player downloads also default to normal matchmaking and accept the same explicit CLI alternatives, while storage retains every downloaded mode. `None` on either library argument lifts that half of the filter. Readable names come off the compiled protobuf enum (`queries.match_mode_name` / `game_mode_name`, `extract.MATCH_MODES` / `GAME_MODES`) — never hardcode a dict, the enum already gained `Calibration` that way
  - <a id="matches.not-scored"></a>`matches.not_scored`: Valve's own flag with at least two verified triggers: a safe-to-leave after an early abandon (the common case, short games), and a cheat conviction voiding an otherwise completed game (verified once: a full-length ranked game where the `Parry Success`/`Parry Miss` custom stats ran 43-81 successes for the convicted side against single digits for everyone else — auto-parry). The flag does NOT hide the result: `winning_team` stays set, match history can still show the W/L, and `rewards_eligible` stays true — most likely it means no rating adjustment. `deadlock winrate` leaves these out of the table and reports them under it (`queries.unscored_record`)

- `stats` — per-sample snapshots. Take the last sample by `time_stamp_s` per match/player, never `max()`: `net_worth`, `max_health`, `weapon_power`, and `tech_power` can fall after a death or sold item, so their peak is not their final value. `queries.stat_snapshots` and `queries.final_stats()` apply this collapse. Sample times are exact and identical in every archived match: every 3 minutes through 15:00 (180, 360, ..., 900), every 5 minutes from 20:00 on (1200, 1500, ...), plus one final off-grid sample at match end. `soul_sources` and `custom_stats` ride the same snapshot clock; `damage_sources` does NOT (its own ~3-min per-source clock, no late-game switch). The two grids share 900, so 5-minute intervals align exactly from 15:00 on — before that, gains land in the interval holding the recording sample (the printed 0-5/5-10/10-15 rows really cover 0-3/3-9/9-15). Intervals finer than the local cadence just forward-fill (zero-gain rows, then a lump). Verified caveats:
  - <a id="stats.snapshot-scoreboard-drift"></a>snapshot `kills` drifts from the scoreboard in roughly a third of player-games (±1 to ±4). It is the mirrored half of the Rejuvenator mechanic below, not a second mechanism. Killing a player who holds a Rejuvenator credit is not an official kill — it shows no kill in the HUD and grants no souls — but the engine still fires the hero-kill event, which is why on-kill effects (Shiv's Killing Blow reset, Grey Talon / Mo & Krill / Vindicta ultimate stacks, Drifter's Bloodscent) still trigger. The live snapshot counters ride that engine event while the scoreboard counts only official kills, so nothing is ever reversed and the drift lands on OPPOSITE teams. Measured across single-claim matches, the revived side carries the death drift (44.2% of player-games, mean +0.51, against 8.2% for the other team) while the killing side carries the kill drift (31.1% over, mean +0.31, against -0.11). Matches with no mid boss kill barely drift at any length (2.5-5.6%). Counting `deaths` rows by `killer_account_id` matches the scoreboard on 10,313 of 10,332 player-games, so that's the kill source `match_intervals` uses. Not a post-victory artifact — the final sample lands exactly at match end in 14,760 of 14,760 player-games, so nothing scores after it. Open residual: the claiming team also runs slightly UNDER on kills (13.1%, mean -0.11). Three explanations are already ruled out — it is not post-victory scoring (above), not a winner effect (claiming+lost -0.02 vs non-claiming+won +0.35, so it tracks the claim and not the result), and not the revive rolling back the revived player's own counters (revived and non-revived claiming-team players under-count identically, -0.105 vs -0.119). It is team-level and tracks the Rejuv claim; the cause is unknown
  - snapshot `deaths` also counts Rejuvenator self-revives, which the scoreboard doesn't (1-3 extra in ~26% of player-games; 93% of extra ticks follow an own-team Rejuv claim, carry no `gold_death_loss`, and have no `death_details` entry). The `deaths` table, exported from `player.death_details`, matches the scoreboard exactly
  - `net_worth` trails the scoreboard on 22.8% of player-games, always low and nearly always trivially so (median -11 souls, 0.025% of net worth; 303 player-games past 100 souls, 6 past 1,000, max 2,457). NOT because the last snapshot lands early — it lands exactly at match end in 14,760 of 14,760 player-games — so this is income settling in the final instant. Take `players.net_worth` for a final figure
  - `creep_kills` is lane creeps only — the scoreboard's `last_hits` counts creeps + neutrals + more, so never compare snapshot creep_kills to a "last hits" figure (top-level `player.last_hits` is the real one)
  - snapshot timestamps skew a few seconds early against event times (a death at t=182 lands in the t=180 snapshot) — use ~10s tolerance when bucketing events into snapshot windows
  - protobuf `gold_*` renamed `souls_*`. Accuracy = `shots_hit / (shots_hit + shots_missed)`, headshot rate = `hero_bullets_hit_crit / (hero_bullets_hit + hero_bullets_hit_crit)`

- <a id="soul-sources.cumulative-snapshots"></a><a id="soul-sources.include-orbs"></a>`soul_sources` — per income source per snapshot (`source_name` = troopers/jungle/breakables/...). The in-game number is `souls + souls_orbs`, ALWAYS sum both. `souls` is the guaranteed portion; `souls_orbs` is the deniable flying-orb portion you SECURED. Two different quantities, don't conflate them:
  - design ratio (share of trooper bounty placed in the orb): 40% before the 2026-06-30 patch, 50% after (from the patch notes)
  - secured share (`souls_orbs / (souls + souls_orbs)`, what you actually kept): lower, because orbs get denied/missed — measured medians run ~27% before, ~30% after, with individual matches swinging past 40%
  - never pin a fixed figure — the sum-both rule is invariant, the magnitude drifts by patch and by how well the player confirms orbs. The `soul_source_games` view and the `queries` soul helpers already sum both, this applies to ad-hoc polars
  - source 7 (denies, screen label "Denies") is TEAM-shared income: every teammate gets ~9-10 souls per denied orb, and it hits zero only when the whole team never denies (verified across the archive, flat `souls_denied` equals it exactly and its `souls_orbs` is always 0). A player with 0 scoreboard denies still earns these, so never read it as personal denying — the scoreboard `denies` column is the personal count

- <a id="item-events.historical-pricing"></a><a id="item-events.ownership-windows"></a>`item_events` — buys with names/cost/tier. `attribution` marks how an item's value shows up: `proc` = has its own damage rows (Scourge, Escalating Exposure), `stat` = never appears as a source, value hides inside other rows (Boundless Spirit, Echo Shard). `cost`/`tier`/`slot` resolve as-of match time from dated asset snapshots (`assets_date` says which; null = no history covered that match yet), so a balance patch doesn't reprice history. Ownership windows run from buy time to sell/consume time, or match end when kept; the query helpers apply this consistently

- <a id="damage.final-totals"></a>`damage` — per dealer/source/target, the FINAL match-end totals with no time axis, so a plain sum by source is safe. This is the totals table — reach for it for any "how much damage from X" number, never `damage_sources`. The `damage_source_games` view aggregates it per source and `hero_damage_games` per dealer and target, and `queries.source_totals` is the frame under them. `stat` names the figure (damage/healing/mitigated/...):
  - <a id="damage.detail-vs-total"></a>`category` splits screen-level `total` rows ("Bullet", "Ability", "Melee") from `gun`/`ability`/`item` detail rows — summing totals with details double-counts
  - `delivery` groups detail rows for gun-vs-spirit questions: `gun`, `gun_proc` (on-hit items like Mystic Shot/Headhunter/Toxic, even when spirit-typed), `ability`, `spirit_proc`. Gun headshots are the `_crit` source ("Promises Kept (crit)")
  - <a id="damage.hero-targets"></a>ALWAYS filter `target_account_id.is_not_null()` for hero damage — null target = NON-PLAYER (creeps/objectives, raw slot 0). Without it farm damage inflates every source (creep headshots once made gun-crit look 9× body). Hero-only detail sums reconcile with snapshot `player_damage`
  - healing rows (`stat == "healing"`): NO base hero regen or fountain regen exists anywhere (verified: `player_healing` equals the source sum in every player-game checked). Item regen IS included and credited to the item (Fortitude, Radiant/Mystic Regeneration). A source in a player's block does NOT imply ownership — Spirit Shredder Bullets grants allies spirit lifesteal so its class lands in non-owner blocks, and Ivy's Kudzu tether splits credit between Ivy and each tethered player

- `damage_sources` — the damage table's sources over TIME, cumulative per (dealer, source, stat) sample like the in-game damage graph. This is the timeline table, NOT a totals table: `damage` is a running total, so summing a source across its `time_stamp_s` rows multiplies by the sample count (~5× overcount). For a total take the last sample per source, use the `damage` table, or summarize the `damage_source_games` view; for a timeline use `queries.source_intervals`/`damage_intervals`, which diff it into the view behind `deadlock match --damage` and reproduce the in-game tooltip exactly. Summed over targets with a `vs_heroes` split instead of per-target rows; same `category`/`delivery` columns, so keep the total-vs-detail filter. Samples are sparse (~3 minutes apart plus match end) and the protobuf arrays are RIGHT-aligned to `sample_time_s` — the export already handles the alignment. Final sample == the `damage` table value

- `objectives` — one row per team objective (Guardian/Walker/Base Guardians/Shrine/Patron/Weakened Patron) with `team`, `lane` (color, derived empirically: engine lane ids 1/3/4 = yellow/blue/green, verified three ways against attacker positions 2026-07-07), `destroyed_time_s` (null = survived), `first_damage_time_s`, and the player/creep damage split. Backs the `deadlock match --teams` log
  - `player_damage` is TOTAL hero damage (gun and spirit combined); `player_spirit_damage` is the spirit portion, a subset that never exceeds it (verified across the whole archive). Both are per objective, summed over ALL attackers — no per-player split exists in the metadata. The proto's `player_damage_mitigated`/`creep_damage_mitigated` are zero on every objective ever checked — dead fields, don't hunt for them

- `mid_boss` — one row per midboss (Rejuvenator) kill: `destroyed_time_s`, `team_killed`, `team_claimed` (differs from team_killed when stolen).
  - the in-game reward has been multi-part across patches (3 dropped crystals in mid-2025, later one crystal granting 3 shared revive credits) but the protobuf only ever records ONE claiming team per boss kill — a split pickup is not representable, so never present `team_claimed` as "got all the rejuvs". Claims per team is the only trustworthy rejuv metric
  - revives *consumed* (`max(snapshot deaths) - scoreboard deaths` per player) is deliberately NOT exported — 7% of those ticks provably can't be rejuv revives (players with more ticks than own-team claims), so don't present it as a rejuv count

- `movement` — OPT-OUT via the config exclude list (the starter config excludes it). ~330KB and ~26k rows per match, ~85% of export time before vectorization. If movement.parquet is missing, `queries.table_exists("movement")` is False and `deadlock deaths` drops its context columns instead of failing.
  - every player's per-second track from `match_info.match_paths`: `x`/`y` world units, `health_percent` (0-100, 0 while dead), `combat_type` (out/player/enemy_npc/neutral), `move_type` (normal/ability/ability_debuff/ground_dash/slide/rope_climbing/ziplining/in_air/air_dash)
  - LEFT-aligned, unlike the damage matrix: sample index = game second (verified against death positions, median error ~209 units at offset 0 vs ~8000 one second off). Trailing samples past `duration_s` are end-screen noise, already dropped at export
  - positions are quantized to a per-player 14-bit bounding box (~200-unit jitter); there is no z. Velocity = distance between consecutive seconds; clamp respawn/zipline teleport spikes before averaging
  - movement-tech profiles (slide%, dash/min, air-dash/min) vary strongly BY HERO — normalize per hero before comparing players

- <a id="movement.hero-dependent"></a>`movement_intervals` — always built (even with movement excluded), one row per player per minute of counts from alive seconds: `alive_s`, `moving_s`, `stationary_s` (steps under 40 units), `slide_s`/`in_air_s`/`zipline_s`, `combat_s` (fighting players), `dashes`/`air_dashes` (transitions into the state), `distance` (world units, zipline seconds and teleport-sized jumps skipped). ~60x smaller than movement. Counts, not percents, so any bucketing that is a whole number of minutes sums exactly — the `movement_games` view aggregates them per game, and `queries.movement_intervals` and `queries.movement_profile` derive the percents. Steps and transitions are computed on the whole 1 Hz sequence before the minute grouping, so sums reproduce whole-match numbers exactly. Movement profiles vary strongly by hero, so compare within a hero or normalize by hero

- `deaths` — one row per death from `player.death_details`: `game_time_s`, `time_to_kill_s`, `death_duration_s` (respawn timer), `killer_account_id` (null = non-player), death `x`/`y`/`z` and `killer_x`/`y`/`z`. This is the death record that matches the scoreboard (snapshot `deaths` overcounts, see `stats` above). Join to `movement` at `game_time_s` to count allies/enemies within radius at the moment of death (~2000 units = in the fight; enemies with `combat_type == "player"` in the preceding seconds were participants, not bystanders)

- <a id="custom-stats.cumulative-snapshots"></a>`custom_stats` — the named counter pool (`custom_user_stats` on the wire), one row per stat per player per snapshot, cumulative like the stats table. Absent = zero, the game only emits nonzero counters. The `combat_games` view pivots the fight counters out of it per game, and `queries.custom_stats` collapses to final values by default (`final=False` for the snapshot rows). Backs `deadlock match --combat`
  - wire stat ids are registered PER MATCH — the same name lands at different ids in different matches, and hero/mode mix changes which ids exist. The export resolves ids through each match's own registry (`extract.custom_stats`), so the table only carries names; never aggregate raw protobuf custom stats by id
  - names namespace as `Group##Stat`, split into the `group`/`stat` columns (bare names like `Parry Success` keep a null group). New groups appear as Valve adds them (per-hero counters like `Celeste##RadiantDaggerTimeAt_N_stacks` are uptime seconds per stack count) — consumers must stay name-agnostic
  - every family is a cumulative count EXCEPT the `Bullet Stats` groups, which are percents recomputed per snapshot (non-monotonic on the wire) — never diff those, and recompute rates from the `Enemy Hero Accuracy` counts when a windowed rate is needed
  - <a id="custom-stats.parry-includes-counterspell"></a>`Parry Success` counts more than melee duels: Counterspell upgrades parry into a 0.8s spell parry and every ability/item hit blocked increments the counter (owners mean 13.0 and 21% of owner games clear 20, max 335; non-owners max 22 in 9,462 player-games — any value past ~22 is a Counterspell game). Rebuttal only makes real parries more frequent (parry cooldown reduction). Join `item_events` before reading big numbers
  - the `* Dist` groups are damage by range band in meters (buckets 10/20/30/40/50/75/100/Infinite); melee and item damage carry no range family, so the outgoing buckets sum to slightly under snapshot `player_damage`
  - `Comeback Gold Koth` is the ONLY metadata trace of the Unstable Rift: a flat amount to each player on one team per rift. `Comeback Gold Urn` died with the 2026-06-30 patch that rethemed KOTH
  - `Unspent Gold Minutes`/`Unspent AP Minutes` are balance-times-minutes integrals — divide by match minutes for the average unspent balance
  - `PowerUp Gold`/`PowerUp Permanent`/`PowerUp Temp` are pickup counters (own pickups only; `power_up_buffs` additionally includes teammates' shared permanent buffs) — buff questions belong to the `buffs` table (the `buff_games` view aggregates it, `stack_games` does the same for `stacks`) and `match --buffs`, `--combat` skips these

## Games from other players → `parquet-players/`

`deadlock download --hero X` writes the SAME tables to the sibling `parquet-players/` dir (api json is field-identical to the local decode, so every query pattern here applies unchanged).

- before running, check whether coverage is already fresh — another session or agent may share these dirs and have just downloaded: `scan("downloads", players.PARQUET_DIR).group_by("player").agg(pl.col("downloaded_at").max(), pl.col("match_id").max())` (join matches for the latest game date); only download if the window you need is missing
- re-runs skip persisted match bodies but still hit leaderboard + match-history endpoints and rebuild every table
- query with `queries.scan(table, players.PARQUET_DIR)`. The extra `downloads` table records which player's history brought each match in, their rank/region at download time, and `downloaded_at` (= patch era; null rank = never on the leaderboard at download). The tables are a chosen sample, not the full history of those players — check `downloaded_at` before comparing across patches
- the ledger holds MORE than the comparison pool: old `--account` downloads and `--match` rows stay forever, while the CLI comparisons read only accounts currently under `[players.<Hero>]` in config.toml (`players.pool_games` applies that filter — reuse it instead of scanning the raw ledger when the question is about the pool)
- `players.tracked_player_games(["somename"], hero="Mirage")` does the downloads→players→matches join for you (that player's own rows among all 12 per match, ledger names case-insensitive, local `day` included)
